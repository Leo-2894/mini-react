먼저 기능을 보고, 필요한 개념을 이해한 다음, 실제 코드와 화면에서 확인하세요. 개발 일지 전체를 읽는 대신 과제 핵심 로직을 자신의 말로 설명하는 것이 목표입니다.

  1. Phase 1: 편집한 화면의 차이를 어떻게 찾아 적용할까?
  2. Phase 2: 함수가 다시 실행돼도 상태는 어떻게 유지될까?
  3. 두 단계 연결: State가 만든 화면도 같은 Diff/Patch를 쓸 수 있을까?

우리가 만든 결과물과 과제 개념

엔진을 만들고, 두 화면에서 사용했습니다

과제 필수: DOM↔VDOM, 다섯 변화 유형, Diff/Patch, 양 영역 History, FunctionComponent, 루트 State와 세 Hook, 같은 엔진 재사용, 단위·기능 시험입니다. 선택: Batching입니다. REST 통신·취소·이력 정제는 주제 자유인 웹페이지를 API 도구로 구현하면서 추가한 기능입니다.

왜 학습 순서를 Phase 1 → Phase 2로 잡을까?

먼저 “다음 화면 객체를 실제 DOM에 반영하는 방법”을 만듭니다. 그다음 “변경된 State에서 다음 화면 객체를 얻는 방법”을 얹습니다. 이렇게 나누면 Hook이나 HTTP 요청이 엔진을 대신하지 않는다는 점이 보입니다.

이것은 과제의 두 단계와 실제 공통 import를 연결한 학습 설명입니다. 과거 개발자의 기록되지 않은 선택 이유를 재구성한 것이 아닙니다.

학습 확인: Diff와 Patch를 왜 구분할까요?

같은 p의 글자가 A → B로 바뀌었다고 가정하세요. Diff의 출력은 “기존 text Node의 내용을 B로 바꿔라”라는 계획입니다. Patch는 그 계획으로 실제 Node.data를 수정합니다. p 전체를 새로 만들 필요는 없습니다.

직접 설명하기: VDOM 생성, Diff 완료, Patch 완료 중 실제 화면이 바뀌는 시점은 언제인가요? 답은 Patch에서 실제 DOM 쓰기가 일어나는 시점입니다.

학습 확인: useState · useEffect · useMemo를 구분해 보세요

useState = 바뀌는 값 유지

URL·탭·로딩·응답을 저장합니다. setter는 queue와 루트 재실행을 예약합니다.

useEffect = 외부 동작과 정리

job이 바뀌면 요청을 시작합니다. 이전 요청이나 이벤트 listener는 cleanup으로 정리합니다.

useMemo = 같은 계산 결과 재사용

draft가 같으면 요청 검증 결과를 재사용합니다. App 실행 자체를 막는 기능은 아닙니다.

같은 순서 = 같은 Hook 슬롯

함수 지역 변수는 새로 생겨도 인스턴스의 hooks 배열은 남습니다. 호출 순서로 같은 상태를 찾습니다.

학습용 예측: 초기0에서 set(n => n + 1)을 한 동기 이벤트에서 세 번 호출하면, queue는 앞 결과를 이어받아3을 만들고 한 번의 예약 update로 반영합니다. 실제 제품에 Counter 화면이 있다는 뜻은 아닙니다.
