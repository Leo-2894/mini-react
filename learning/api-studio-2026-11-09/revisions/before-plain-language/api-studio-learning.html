과제 핵심Document · Window · Node: 화면을 읽고 바꾸는 대상은 무엇인가?

DOM(Document Object Model)은 브라우저가 문서를 객체들의 트리로 표현한 것입니다. HTML은 문자열이고, DOM은 부모·자식·형제 관계를 가진 실제 객체입니다. 같은 태그 문자열을 가진 두 요소도 서로 다른 Node일 수 있습니다.

Document는 현재 문서의 조회·생성을 담당합니다. document.querySelector는 요소를 찾고, createElement는 요소를 만들고, createTextNode는 글자 노드를 만듭니다. Window는 브라우저 창의 전역 객체입니다. window.document가 현재 문서이며 창 전체 keydown 같은 이벤트를 받을 수 있습니다. Node.js의 전역 환경과는 다릅니다.

트리에서 글자도 별도의 Node입니다

<section><p>안녕</p></section>
section (Element)
└─ p (Element)
   └─ "안녕" (Text)

children은 요소 자식만 보지만 childNodes는 Text와 Comment도 포함합니다. 우리 domToVNode는 nodeType으로 Element·Text·Comment를 구분하고, childNodes를 재귀적으로 내려갑니다. 재귀는 자식에게 같은 읽기 과정을 반복하고, 자식이 없는 텍스트에서 멈추는 방식입니다. 이 덕분에 중첩 HTML과 의미 있는 공백을 읽습니다.

읽기와 쓰기 API를 구별하세요

getAttribute·childNodes 조회는 읽기입니다. setAttribute/removeAttribute는 속성 쓰기, Text.data 대입은 글자 쓰기, appendChild/insertBefore/removeChild는 구조 쓰기입니다. insertBefore에 이미 있는 Node를 넘기면 그 Node를 이동합니다. 부모의 textContent 대입은 자식 구조를 없앨 수 있어, 우리 Patch의 텍스트 변경은 결속한 Text Node의 data만 바꿉니다.

사용 기능: DOM Lab의 초기 샘플 읽기와 테스트 영역 생성, Patch의 부분 갱신입니다. ownerDocument는 해당 Node가 속한 문서를 뜻해 그 문서에서 새 Node를 만들게 합니다. API Studio의 키보드 단축키는 window listener로 처리합니다.

설명할 문장: “HTML을 그대로 비교한 것이 아니라, 실제 Node 트리를 읽어 비교 가능한 데이터로 바꿨다.”

과제 중점이벤트와 MutationObserver: 사용자 행동과 DOM 변화는 어떻게 다른가?

이벤트는 click·input·change·keydown 같은 발생 사실을 listener에 전달합니다. API Studio는 input 이벤트에서 현재 입력값을 읽고 부모 callback을 호출합니다. 브라우저의 입력 동작과 이를 state에 반영하는 작업은 별개입니다.

MutationObserver는 DOM 트리의 구조·속성·텍스트 변경 기록을 관찰하는 브라우저 API입니다. 누가 클릭했는지가 아니라 무엇이 바뀌었는지를 봅니다. childList는 자식 추가·삭제, attributes는 속성, characterData는 Text/Comment 내용, subtree는 하위 트리까지의 관찰을 뜻합니다. 일반 callback 통지는 즉시 동기 호출이 아니며, takeRecords로 아직 전달하지 않은 기록을 꺼낼 수도 있습니다.

학습용으로 단순화한 관찰 설정:
observer.observe(host, {
  childList: true, attributes: true,
  characterData: true, subtree: true
});
renderer.render(변화가_없는_Tree);
observer.takeRecords();  → [] 이어야 함

이 프로젝트에서 쓰인 곳: 제품의 자동 동기화가 아니라 테스트입니다. Patch 후 화면 글자가 같아도 내부적으로 지웠다 다시 만들 수 있습니다. no-op 테스트는 변경 기록이 없다는 것과 기존 Node 참조가 같다는 것을 함께 확인합니다.

한계: input.value 같은 live property 대입은 일반적인 attribute 변경 기록과 같지 않습니다. 따라서 live property의 불필요한 쓰기는 setter spy 등으로 따로 검사합니다. DOM Lab은 observer 기록을 VDOM 대신 쓰지 않고, Patch를 누를 때 현재 편집 DOM 전체를 다시 읽습니다.

과제 중점Reflow · Repaint: 실제 DOM 작업은 왜 비용이 들 수 있는가?

DOM 객체에 값을 대입하는 비용만 있는 것이 아닙니다. 스타일이 달라지면 브라우저는 필요한 스타일을 다시 계산합니다. Layout(Reflow)는 요소의 크기와 위치를 계산하고, Paint(Repaint)는 글자·색·테두리 같은 픽셀을 그립니다. Composite는 그려진 레이어를 합성하는 단계입니다. 이는 렌더링 과정을 이해하기 위한 요약입니다.

예를 들어 요소의 폭이 달라지면 주변 배치까지 다시 계산할 수 있습니다. 배치가 그대로인 색 변경은 보통 다시 그리는 작업이 중심입니다. transform 등은 조건에 따라 합성 단계에서 처리될 수 있습니다. 모든 DOM 쓰기가 전체 페이지의 모든 단계를 즉시 실행하는 것은 아닙니다.

브라우저는 여러 변경을 모아 처리하기도 합니다. 그러나 스타일을 쓴 직후 offsetWidth 같은 최신 크기를 읽는 일을 반복하면, 필요한 layout을 그때그때 강제로 계산하게 만들 수 있습니다. 이런 읽기·쓰기 반복이 성능을 해칠 수 있습니다.

우리 기능과 연결: 같은 p의 글자만 바뀌면 p를 교체하지 않고 기존 Text를 수정하고, 같은 입력값은 다시 대입하지 않습니다. 목표는 불필요한 DOM 작업과 Node 교체를 줄이는 것입니다. Virtual DOM 객체 생성과 Diff도 계산 비용이 있으므로 항상 직접 DOM보다 빠르다는 뜻은 아닙니다. 이 저장소에는 속도 우위를 입증한 벤치마크가 없습니다.

개념 근거: MDN 브라우저의 렌더링 과정. “필요한 부분만 수정한다”와 “실측으로 더 빠르다”는 구분해서 설명하세요.

과제 핵심Virtual DOM: 화면 객체에는 어떤 정보를 보관하는가?

Virtual DOM(VDOM)은 화면의 구조와 원하는 값을 일반 JavaScript 객체로 표현한 것입니다. 실제 DOM의 복제 객체나 숨겨진 두 번째 화면이 아닙니다. 객체를 만들어도 브라우저 화면은 바뀌지 않습니다. 다음 화면의 설명을 얻고 나서 Diff와 Patch가 이어져야 합니다.

왜 필요한가: App은 “어떤 화면이어야 하는가”를 계산하고, 엔진은 “실제 DOM에 무엇을 써야 하는가”를 담당하게 나눕니다. Phase 1에서 편집 DOM으로 만든 데이터도, Phase 2에서 App이 반환한 데이터도 같은 형식이므로 같은 엔진을 사용할 수 있습니다.

우리 VNode 필드를 하나씩 읽기

  • kind: element·text·comment 중 노드 종류입니다.
  • tag / attrs: 요소 종류와 class·id 같은 HTML 속성입니다.
  • props / events: 현재 입력값 같은 live 값과 listener 함수입니다.
  • children: 아래쪽 VNode 목록입니다. 재귀적으로 같은 구조가 이어집니다.
  • key: 같은 부모의 자식을 이전 렌더와 대응시킬 정체성입니다.

Tree는 고정 host 안의 여러 최상위 VNode를 담는 root 데이터입니다. Tree 자체에 대응하는 새 div를 더 만드는 것은 아닙니다. host는 이미 존재하는 DOM 영역입니다.

h()는 JSX 없이 화면 객체를 만드는 도우미입니다

h('p', { attrs: { class: 'message' } }, '안녕')
→ element VNode 안에 Text VNode 하나

tree(h('p', {}, 'A'), h('p', {}, 'B'))
→ root Tree 안에 형제 VNode 둘

normalizeChildren은 중첩 배열을 펼치고 문자열·숫자를 Text로 바꾸며 null·undefined·boolean을 화면에서 제외합니다. 그래서 조건 ? h(...) : null과 rows.map(...)을 자식으로 넣을 수 있습니다. h는 마법 문법이나 외부 React 함수가 아니라 우리가 구현한 함수입니다.

DOM→VDOM→DOM: readTree가 원본을 읽고, createDOM이 각 VNode를 실제 Node로 만듭니다. 원본 Node와 테스트 Node는 다른 객체지만 논리 구조와 입력 상태는 같습니다. DOM에 등록된 임의 listener를 역추출하는 기능은 없으며 엔진이 가진 events만 관리합니다.

과제 핵심attrs · live props · events: 입력값과 HTML 속성을 왜 나누는가?

Attribute는 요소에 적힌 HTML 속성이고, property는 DOM 객체의 현재 값입니다. 처음에는 같아 보여도 사용자 입력으로 달라질 수 있습니다.

<input value="A"> 에서 사용자가 B를 입력한 뒤:
input.getAttribute('value') → "A"일 수 있음
input.value                 → "B"

VDOM attrs.value: 선언된 속성
VDOM props.value: 현재 입력값

우리 domToVNode는 input·textarea·select의 value, input의 checked, option의 selected를 live props로 읽습니다. syncProps는 실제 값이 달라졌을 때만 대입합니다. 매번 value를 다시 쓰지 않는 것은 입력 커서와 selection을 지키는 데도 중요합니다.

주의: attribute와 property가 항상 완전히 독립인 것은 아닙니다. checkbox/radio의 value나 input type 전환에서는 property 대입이 content attribute에도 반영될 수 있습니다. 엔진은 자신의 쓰기로 생긴 예상 물리 속성을 별도로 기억해, 외부에서 바뀐 속성과 구별합니다. 사용자에게 보이는 논리 Tree를 그때그때 바꿔 숨기는 방식은 아닙니다.

events에는 click·input 같은 이벤트명과 함수 참조를 넣습니다. HTML의 onclick 문자열을 저장하지 않습니다. syncEvents는 이전 함수와 새 함수를 비교해 바뀐 listener는 제거하고 새 것을 등록합니다. 삭제된 subtree의 listener도 정리합니다.

DOM Lab에서 필요한 이유: 사용자가 contenteditable·Inspector·input으로 현재 DOM을 바꿉니다. Patch는 오래된 문자열이 아니라 candidate()로 이 DOM을 다시 읽어야 합니다. 실제 영역은 엔진이 마지막으로 확정한 committedTree와 대조해 외부 구조 변경을 검출합니다.

과제 핵심Diff: 두 트리를 어떤 순서와 기준으로 비교하는가?

Diff는 이전 Tree와 다음 Tree를 받아 차이를 명령 데이터로 만드는 과정입니다. 우리 diff는 DOM을 직접 읽거나 쓰지 않습니다. 입력 Tree를 변경하지 않고 구조를 복사·동결한 PatchPlan을 반환합니다. 계산 결과를 독립적으로 검증할 수 있게 하는 경계입니다.

형제 대응 → 종류 확인 → 내부 비교

  1. 이전 Tree에 전위 순회 번호를 붙입니다. 부모를 먼저 방문하고 그 자식을 순서대로 방문합니다. 이 번호는 기존 Node를 가리키는 old 참조가 됩니다.
  2. 같은 부모의 자식을 대응시킵니다. key가 있으면 key Map에서 찾고, 없으면 key 없는 형제끼리 순번으로 대응합니다.
  3. 대응이 없거나 kind/tag가 다르면 CREATE로 새 subtree를 준비합니다.
  4. 같은 Text/Comment라면 내용만 비교합니다. 같은 요소라면 attrs/events를 비교하고, children을 재귀 비교하고, props도 비교합니다.
  5. 최종 자식 참조 순서가 이전과 다르면 CHILDREN 명령을 만듭니다.

텍스트만 달라진 경우

old: p(key='title') 안의 Text "A"
new: p(key='title') 안의 Text "B"
→ 기존 p와 Text를 대응
→ { type: 'TEXT', target: 기존_Text_참조, text: 'B' }

명령은 CREATE·TEXT·ATTRS·EVENTS·CHILDREN·PROPS입니다. 삭제는 최종 children에서 기존 참조를 빼는 방식이고, 교체는 새 참조를 넣는 방식입니다. 과제의 다섯 변화 유형이 다섯 명령으로 그대로 구현되는 것은 아닙니다.

한계: key는 같은 부모 안에서 사용합니다. 다른 부모로 옮긴 노드를 전역에서 찾아 재사용하지 않습니다. 전체 트리의 최단 편집 경로나 최소 이동 횟수도 보장하지 않습니다. “변경 없는 노드 재사용과 필요한 부분 갱신”이 우리 구현의 정확한 설명입니다.

과제 핵심Patch: 계획을 실제 DOM에 적용하면서 정체성을 지키는 방법

Patch는 Diff가 만든 명령을 실제 DOM API로 실행하는 단계입니다. renderer는 마지막으로 성공한 committedTree와 revision을 기억하고 preview로 계획을 발급한 뒤 commit합니다. render는 이 두 단계를 연결한 편의 함수입니다.

쓰기 전에 검사하고 실제 Node를 결속합니다

Preflight는 적용 전에 대상 DOM의 종류·태그·텍스트·속성·자식 수가 계획의 oldTree와 맞는지 확인하는 검사입니다. 모든 old 참조를 실제 Node 객체에 미리 묶습니다. 이전 렌더에서 만든 오래된 계획이나 다른 renderer의 계획, 이미 적용한 계획도 거부합니다.

기존 형제: [A, B, C]
다음 형제: [B, C!]
안전한 방법: A/B/C 실제 참조 확보 → A 제거 → 확보한 C의 Text 수정
위험한 방법: A 제거 → 옛 index 2로 C를 다시 찾기

새 subtree는 먼저 만들어 둡니다. TEXT·ATTRS·EVENTS를 반영하고, 자식의 CHILDREN 계획부터 처리합니다. 최종 자식 목록에 없는 Node는 제거하고, 기존 Node를 올바른 순서로 insertBefore 합니다. 마지막에는 트리를 따라 live props를 맞춥니다. 변화가 없는 prop은 재대입하지 않습니다.

같은 모습과 같은 Node는 다른 조건입니다

새 input을 만들어 같은 글자를 채워도 이전 input === 새 input은 false입니다. listener·focus·caret 같은 상태가 달라질 수 있습니다. 우리 Patch는 같은 정체성과 종류의 Node를 재사용하고, 남아 있는 활성 입력의 focus/selection을 가능한 범위에서 보존합니다. 삭제되거나 다른 종류로 교체된 입력까지 같은 Node로 유지하는 뜻은 아닙니다.

오류 경계: 쓰기 전 검사 실패는 보통 기존 DOM을 보존합니다. 실제 쓰기가 시작된 뒤의 예상 밖 실패는 부분 적용일 수 있어 잠그고 오류를 드러냅니다. 자동 전체 재생성으로 복구했다고 주장하지 않습니다. 이 차이는 “성공 상태만 확정한다”는 History와 Hook 동작의 기반이기도 합니다.

과제 핵심State History: 스냅샷과 cursor로 Undo/Redo를 구현한다

Snapshot은 그 시점의 성공한 Tree를 독립적으로 보관한 값입니다. Cursor는 현재 선택한 snapshot의 배열 위치입니다. 사용자가 지금 편집 중인 draft와 성공한 snapshot을 나누어야 Patch하지 않은 내용이 과거 상태를 덮지 않습니다.

createHistory는 Tree의 구조를 복사·동결해 저장합니다. 원본 객체를 나중에 바꿔도 과거 상태가 같이 변하지 않아야 하기 때문입니다. 함수인 events 참조는 유지하므로 JSON.stringify/parse만으로 복사하지 않습니다. History를 이동해도 DOM 객체 자체를 저장해 되붙이는 것이 아니라 Tree에서 같은 Diff/Patch로 양 영역을 갱신합니다.

저장 목록 [S0, S1, S2], cursor=2
Undo → cursor=1, 양 영역을 S1로
여기서 변경 없는 Patch → [S0, S1, S2] 유지 → Redo 가능
여기서 새 S3 Patch    → [S0, S1, S3]      → 옛 S2 폐기

no-op 검사를 미래 분기 삭제보다 먼저 합니다. 실제 변경도 없는 버튼 클릭 때문에 Redo를 잃으면 안 됩니다. 기본 한도는 초기 상태를 포함한 50개이고, 한도를 넘으면 가장 오래된 snapshot을 제거합니다. 증가하는 snapshot id와 현재 배열 index는 같은 개념이 아닙니다.

성공 조건: apply는 실제 반영 뒤 append하고, travel은 두 영역 반영이 성공한 뒤 cursor를 옮깁니다. 이동 전 현재 edit DOM을 다시 읽어 정책을 확인합니다. restoreDraft는 현재 snapshot으로 편집 영역의 미적용 변경을 되돌리는 경로입니다.

이름 주의: 이것은 DOM Lab의 메모리 History입니다. 브라우저 주소의 history.back()이나 API Studio의 최근 요청 metadata 이력과는 다른 자료구조입니다.

구현 연결key와 id: 목록 정체성과 문서 연결은 왜 다른가?

key는 Diff가 같은 부모 아래에서 “이전의 어떤 항목인가?”를 알아보는 값입니다. Params 행은 생성 시 row.id를 정하고 이후에도 같은 key를 씁니다. 첫 행을 지워 두 번째 행이 앞으로 와도 그 행은 원래 Node로 남습니다. 배열 index를 key로 쓰면 위치가 곧 정체성이 되어 입력 상태가 다른 항목과 섞일 수 있습니다.

HTML id는 문서에서 label·CSS selector·ARIA 같은 연결이 대상을 찾는 값입니다. key와 목적이 다릅니다. 우리 엔진의 key는 data-key라는 예약 속성으로도 관리되지만 HTML id를 대신하지 않습니다.

같은 논리 화면 두 개를 한 문서에 놓을 때

DOM Lab의 실제·테스트 영역은 같은 논리 id를 가져도 서로의 label이나 설명을 참조하면 안 됩니다. 그래서 VDOM/History/Inspector에는 논리 id/for/지원 ARIA IDREF를 보존하고, 실제 DOM에는 host별 서로 다른 물리 id를 적용합니다. 예를 들어 논리 consent가 실제 영역의 물리 A와 편집 영역의 물리 B로 대응하며 각 for도 같은 영역의 대상을 가리킵니다. A/B는 설명용 표기입니다.

이때 label.control, input.labels, 접근성 이름이 해당 영역의 control에 연결됩니다. radio는 같은 name의 그룹이 영역 사이에 섞이지 않도록 별도 native form owner로도 나눕니다. ID 연결과 radio 그룹은 다른 브라우저 규칙이므로 별도로 처리합니다.

이는 과제의 별도 필수 알고리즘이 아니라, 두 DOM 영역을 독립적으로 실험하게 하는 실제 적용 사례입니다. 기본 renderer는 scope 없이 기존 방식으로 동작하며 Phase 2도 같은 엔진을 사용합니다. 실제 스크린리더의 사용성까지 시험했다는 뜻은 아닙니다.

입력창과 Send 버튼으로 Component · State · Hooks를 배웁니다

URL·선택 탭·로딩·응답은 바뀌는 데이터인 State입니다. App이 이를 소유하고 자식은 props로 받아 화면을 만듭니다. 함수가 다시 실행돼도 값이 남는 이유를 Hook 슬롯에서 찾아보세요.

과제 핵심FunctionComponent: 함수와 인스턴스의 역할을 나눈다

함수형 Component는 props를 받아 UI를 설명하는 VNode를 반환하는 함수입니다. FunctionComponent 클래스는 그 함수를 실행하고 지속 정보를 보관하는 우리가 만든 실행 관리자입니다. 사용자 UI를 클래스 컴포넌트로 만들었다는 뜻은 아닙니다.

App(props) → 다음 VNode
new FunctionComponent(App) → App을 실행할 인스턴스
인스턴스에 남는 것: hooks / queues / props / renderer / 예약 정보
호출마다 새로 생기는 것: 지역 변수 / callback / 새 VDOM

mount(host)는 비어 있는 host와 renderer를 연결하고 최초 update를 합니다. update()는 queue 계산·App 실행·공유 renderer 호출·성공한 Hook 확정을 수행합니다. updateProps는 다음 props를 예약해 같은 갱신 경로로 보냅니다. unmount()는 예약 작업을 무효화하고 effect cleanup, 빈 Tree 적용, listener와 Hook 정리를 수행합니다.

함수 안의 let count = 0만으로는 호출할 때마다 초기화됩니다. useState는 외부에 살아 있는 해당 인스턴스의 hooks 슬롯에서 값을 가져옵니다. 따라서 인스턴스 수명과 현재 함수 호출의 수명이 다릅니다. 서로 다른 루트는 서로 다른 hooks 배열을 가집니다.

setter는 슬롯 index와 mount generation을 closure로 기억합니다. Closure는 함수가 만들어질 때의 주변 변수를 나중에도 참조하는 기능입니다. 이전 mount의 setter나 이미 예약된 microtask가 unmount 뒤 DOM을 되살리지 않도록 generation과 ticket을 검사합니다. 전역에는 현재 Hook 호출 권한 같은 일시적 문맥만 있고 모든 App의 지속 state를 하나로 공유하지 않습니다.

과제 핵심Component 분리 · props · Lifting State Up: 데이터는 아래로, 변경 요청은 위로

컴포넌트 분리는 화면을 역할이 분명한 작은 함수로 나누는 일입니다. 모든 div마다 함수를 만들기보다, 입력·응답·이력처럼 책임과 필요한 데이터가 다른 단위를 고릅니다. 이 프로젝트는 App 아래 Sidebar, RequestEditor, ResponsePanel을 두고 입력 행과 JSON 표시를 더 작은 함수로 나눕니다.

Props는 부모가 자식에게 전달하는 입력입니다. 값뿐 아니라 onSend·onDraft 같은 함수도 전달합니다. Stateless 자식은 자체 state를 저장하지 않습니다. 순수한 렌더 함수는 props를 읽어 VDOM을 계산하며 render 자체에서 Fetch나 외부 DOM 변경을 하지 않습니다. 반환된 이벤트 callback이 나중에 실행되는 것과 render 중 부작용은 구분합니다.

Lifting State Up은 함께 쓰는 데이터를 공통 부모로 올리는 패턴입니다. 이 과제는 더 강하게 모든 State/Hooks를 App 루트에만 둡니다. RequestEditor의 Send와 ResponsePanel의 로딩, Sidebar의 이력이 같은 요청 결과를 사용하므로 App에서 함께 관리합니다.

장점은 변경 원천이 하나이고 여러 영역을 일관되게 바꾸기 쉽다는 것입니다. 비용은 작은 탭 변경에도 App과 자식 함수를 다시 평가한다는 점입니다. 그래도 Diff/Patch가 변화 없는 DOM까지 교체하는 것은 아닙니다. 함수 재실행 횟수와 실제 DOM 변경량은 다릅니다.

h(Child, props)는 wrapper DOM 없이 Child 결과를 평가하고 그동안 Hook 권한을 막습니다. 실제 React의 자식별 state 사용 범위와 다른, 이번 과제의 제약입니다.

기존 검증에서 확인: props 갱신·자식 Hook 거부·Node 재사용

과제 핵심useState: lazy 초기화·안정된 setter·함수형 updater를 구분한다

State는 시간에 따라 바뀌며 화면 계산에 쓰이는 데이터입니다. App에는 draft·tab·loading·response·job·history·expanded 등이 들어 있는 하나의 state 객체가 있습니다. 엔진은 여러 useState 슬롯도 지원하고 테스트하지만, 제품 App이 여러 state Hook을 사용한다고 설명하면 틀립니다.

const [value, setValue] = useState(초기값);
useState(() => 초기값계산())  → lazy initializer
setValue(새값)               → 그 값으로 교체 요청
setValue(previous => 새값)   → 직전 queue 결과로 계산

Lazy initializer 함수는 최초 mount의 해당 슬롯 생성 때 한 번 실행합니다. 매 App 호출마다 초기값으로 덮지 않습니다. 함수 자체를 state 값으로 저장하려면 initializer/updater로 실행되지 않게 함수로 한 번 감싸야 합니다. setValue(() => 저장할함수)가 그 예입니다.

안정적인 setter는 render 사이에도 같은 함수 참조를 유지합니다. 슬롯 생성 때 만들고 이후에 같은 setter를 반환합니다. setter 호출은 현재 지역 변수 value를 즉시 바꾸지 않습니다. action을 queue에 넣고 다음 update를 예약합니다. 이미 실행 중인 callback의 value는 그 render에서 받은 값입니다.

단순 대입보다 해야 할 일이 많습니다

  1. 호출이 허용되는 시점과 유효한 mount인지 검사합니다.
  2. 값 또는 함수 action을 슬롯 queue에 순서대로 저장합니다.
  3. 같은 예약 안의 action을 계산해 다음 state를 얻습니다.
  4. App을 재실행해 다음 VDOM을 만듭니다.
  5. 같은 Diff/Patch로 DOM에 반영한 뒤 Hook 값을 확정합니다.

함수형 updater가 필요한 곳: 비동기 응답과 행 편집은 이전 state의 다른 필드를 함께 보존해야 합니다. App의 set(previous => ({...previous, ...변경}))가 최신 queue 결과를 기준으로 새 객체를 만듭니다. render/updater 안에서 setter를 다시 호출하는 것은 우리 계약에서 금지합니다.

기존 검증에서 확인: lazy 한 번·setter ===·교체/함수 action 순서

과제 핵심useEffect: 성공한 화면과 외부 작업의 수명을 맞춘다

Effect는 화면 객체 계산 밖의 작업을 연결하는 장치입니다. Fetch 요청·window listener처럼 외부 시스템과 연결할 때 사용합니다. App render 중 곧바로 요청하면 나중에 VDOM 검증이 실패해도 요청이 이미 나가고, 무관한 render마다 반복할 수 있습니다.

useEffect(setup, deps)는 render에서 실행할 작업을 슬롯에 기록합니다. DOM Patch와 Hook commit이 성공하면 commitEffects가 바뀐 effect의 이전 cleanup을 모두 실행하고 새 setup을 모두 실행합니다. 우리 엔진은 같은 update 안의 commit 직후 실행합니다. 브라우저가 이미 paint한 뒤라고 보장하지 않습니다.

deps 생략실제 수행된 매 성공 commit 뒤매번 다시 연결해야 할 때. no-op으로 App 자체가 생략되면 실행 없음
[]해당 mount에서 최초 한 번변경될 외부 입력을 읽지 않는 연결
[job]최초와 job 참조가 달라진 commitApp의 요청 작업 수명

sameDeps는 길이와 각 원소를 Object.is로 비교합니다. 객체 내부를 깊게 비교하지 않습니다. setup에서 사용한 변하는 값을 deps에서 빼면 예전 값을 잡은 closure를 계속 사용할 수 있습니다. 반대로 매 render마다 새 객체를 deps에 넣으면 값이 비슷해도 다시 실행될 수 있습니다.

cleanup은 이전 연결을 끝내는 함수입니다

useEffect(() => {
  window.addEventListener('keydown', handler);
  return () => window.removeEventListener('keydown', handler);
}, [외부입력]);

deps 변경 직전의 이전 setup에 대응하는 cleanup, 그리고 unmount 때 마지막 cleanup을 실행합니다. App의 요청 effect는 cleanup에서 active=false와 controller.abort()를 하고, 단축키 effect는 listener를 제거합니다. cleanup은 unmount 때만 실행하는 것이 아닙니다.

setup은 undefined 또는 동기 cleanup 함수를 반환해야 합니다. async setup은 Promise를 반환하므로 우리 엔진이 거부합니다. 비동기 요청은 setup 내부에서 시작하고 별도의 동기 cleanup을 반환합니다. render가 실패하면 새 setup을 실행하지 않습니다. effect 오류는 이미 DOM commit 뒤라 이전 UI로 rollback했다고 할 수 없습니다.

과제 핵심useMemo: 입력이 같을 때 계산 결과와 참조를 재사용한다

Memoization은 같은 입력의 순수 계산 결과를 보관해 다음에 재사용하는 방법입니다. useMemo(factory, deps)는 deps가 같으면 factory를 다시 실행하지 않고 이전 값을 반환합니다. 객체 결과라면 이전 객체 참조도 그대로 돌려줍니다. 컴포넌트 함수 실행 전체를 건너뛰는 기능은 아닙니다.

과제 핵심hooks 배열과 호출 순서: 함수는 새로 실행되는데 값은 어떻게 남는가?

각 Hook 호출에는 변수 이름이 전달되지 않습니다. 엔진은 “이 호출이 url용인가?”를 변수 이름으로 알 수 없습니다. 대신 render 시작마다 hookIndex를 0으로 되돌리고 호출될 때마다 증가시켜 같은 순서의 슬롯을 읽습니다.

state 슬롯에는 value와 setter, memo 슬롯에는 value와 deps, effect 슬롯에는 setup·deps·cleanup 등이 들어갑니다. 함수 지역 변수가 살아남는 것이 아니라 인스턴스의 슬롯 데이터가 남는 것입니다.

조건부 Hook이 위험한 이유

잘못된 형태:

useState('B');

보이기가 true → false가 되면
B가 읽는 순서가 1에서 0으로 바뀔 수 있음

Hook은 루트의 최상위 흐름에서 같은 순서로 호출합니다. 자식·이벤트·initializer·updater·memo factory·effect 안에서 새 Hook을 호출하지 않습니다. 이벤트에서는 이미 받아 둔 setter를 호출합니다. 우리 useSlot은 종류·개수 변경을 DOM commit 전에 거부합니다.

탐지 한계: 종류와 총개수가 같게 유지되는 잘못된 조건 분기까지 모두 찾아내는 것은 아닙니다. JavaScript의 모든 Hook 규칙 위반을 자동 검출했다고 설명하면 안 됩니다. 코드 읽기와 정적 규칙도 필요합니다.

과제 핵심Object.is · 불변 갱신 · Controlled Input: 입력을 state와 연결한다

const a = { url: 'A' };

피할 방식: previous.draft.url = 'B'; return previous;
사용 방식: ({ ...previous,

선택 과제 구현Queue · Microtask · Batching: 세 번 변경해도 한 번에 갱신하는 이유

Queue는 action을 호출된 순서로 보관하는 목록입니다. Batching은 모인 action들을 처리한 뒤 한 번의 update로 화면을 계산하는 방법입니다. 과제에서는 선택 사항이지만 우리 엔진은 구현했습니다.

JavaScript가 현재 이벤트의 동기 코드를 실행하는 동안 setter는 action만 넣습니다. schedule은 pending 표시가 없을 때 queueMicrotask를 한 번 예약합니다. 현재 실행 스택이 끝나 microtask를 처리할 때 update가 실행됩니다. 모든 비동기 작업과 다른 tick까지 영구히 한 번으로 합치는 기능은 아닙니다.

첫 예의 n은 이미 실행 중인 render의 값이라 세 호출 모두 숫자 1을 전달합니다. 둘째 예는 함수를 나중에 실행하면서 앞 결과를 다음 입력으로 넘깁니다. 교체와 함수 action을 섞어도 같은 순서로 계산합니다.

No-op은 두 층입니다. 최종 state가 Object.is로 같고 props 변경도 없으면 App 실행을 생략합니다. App이 실행됐어도 VDOM이 같으면 Diff가 DOM 변경을 만들지 않을 수 있습니다. “함수를 다시 실행했다”와 “실제 Node를 바꿨다”를 구분하세요.

우리 방식은 단순 microtask 예약입니다. 실제 React의 전체 scheduling과 같다고 볼 수 없습니다. 또한 긴 microtask 처리가 반복되면 브라우저에 부담을 줄 수 있어 엔진은 자동 update 루프에도 한도를 둡니다.

과제 핵심Render · Commit · Effect: 계산 성공과 화면 적용 성공을 구별한다

Render는 새 state 초안으로 App과 자식을 실행해 VDOM을 계산하는 과정입니다. Commit은 검증된 변경을 실제 DOM에 적용하고 성공 상태를 확정하는 과정입니다. 우리 renderer.commit과 FunctionComponent의 Hook 확정은 서로 연결돼 있지만 같은 객체의 메서드는 아닙니다.

committed hooks → draft 슬롯 복사
→ action 계산 → App / VDOM 검증
→ renderer.render → 공통 Diff / Patch
→ this.hooks = draft → props 확정
→ 변경 effect의 cleanup 전체 → setup 전체

Hook 종류나 VDOM이 잘못돼 쓰기 전 render가 실패하면 draft를 성공한 hooks로 바꾸지 않습니다. 화면과 이전 memo cache를 유지하고 실패 queue를 버립니다. 그러나 실제 Patch 중 일부 쓰기 뒤 실패와 commit 뒤 effect 실패는 이미 발생한 DOM 변경을 자동 취소한 것이 아닙니다.

두 Phase 공유 지점: Phase 1의 controller도 Phase 2의 FunctionComponent도 동일 createRenderer를 import합니다. 신규 Tree 생성 방법만 다르고, renderer.preview→diff와 renderer.commit→validatePatch→patch는 같습니다. 따라서 Hooks를 위해 별도 DOM 엔진을 만든 것이 아닙니다.

브라우저의 paint는 이 JavaScript 함수 이름과 다릅니다. 함수를 실행했거나 commit했다고 언제든 픽셀이 이미 보였다고 단정하지 않습니다. 이 구별이 useEffect 실행 시점과 오류 처리를 정확히 설명하는 출발점입니다.

제품 응용HTTP · Fetch · Promise · JSON: Hook을 실제 요청 도구에 적용한다

HTTP 요청은 method·URL·headers·body로 구성됩니다. GET은 보통 조회, POST는 생성/처리, PUT은 자원 대체, PATCH는 일부 변경, DELETE는 삭제에 쓰이지만 실제 의미는 서버 계약이 정합니다. API Studio는 이 다섯 method를 선택해 보낼 수 있는 클라이언트입니다. 자체 데이터베이스나 API 서버를 만든 것은 아닙니다.

Query Params는 URL 검색 부분, Headers는 Content-Type 같은 부가 정보, Body는 요청 본문입니다. buildRequest는 URL/URLSearchParams/Headers로 값을 조립하고 JSON 본문을 전송 전에 검사합니다. GET body는 보내지 않습니다. 편집 중 draft와 Send 시점에 검증·고정한 snapshot을 나누어, 응답 대기 중 추가 편집이 이미 보낸 요청을 바꾸지 않게 합니다.

Fetch는 브라우저 네트워크 API이고 Promise는 나중에 얻는 결과를 표현합니다. Send는 job과 loading을 state에 넣고, useEffect([job])가 Fetch를 시작합니다. 기다리는 동안 UI는 멈추지 않고 로딩·취소 기능을 보여 줍니다. 결과를 state에 넣으면 같은 Diff/Patch가 응답 패널을 갱신합니다.

오류 종류를 섞지 않습니다

  • HTTP 4xx/5xx: 서버 응답을 받았습니다. Fetch가 이 status만으로 reject하지 않으므로 status/ok와 body를 보여 줍니다.
  • 네트워크 실패: CORS·DNS·연결 문제 등이 가능하며 보통 응답 status를 얻지 못합니다. 한 오류만 보고 CORS로 확정하지 않습니다.
  • JSON parse 실패: 응답은 받았지만 본문이 JSON 문법과 맞지 않을 수 있습니다. 원문 fallback과 안내를 유지합니다.
  • 취소/timeout: AbortController와 timer로 별도 결과 종류를 표시합니다.

CORS(Cross-Origin Resource Sharing)는 다른 origin의 응답을 브라우저 JavaScript가 사용할 수 있는지 서버 정책으로 결정하는 체계입니다. origin은 scheme·host·port로 구분합니다. 4173 페이지에서 4174 API를 요청하면 다른 origin입니다. 서버 허용이 필요하고, 요청 종류에 따라 사전 OPTIONS 확인도 있을 수 있습니다. 이 앱은 프록시로 우회하지 않습니다.

JSON은 문자열로 주고받는 데이터 형식입니다. JSON.parse로 얻는 값이 곧 HTML은 아닙니다. JsonViewer는 객체/배열을 순회해 VDOM Text로 표시하고 expanded state로 펼침을 관리합니다. 문자열에 태그처럼 보이는 내용이 있어도 innerHTML로 실행하지 않습니다. 표시 행·깊이·문자 제한은 전체 응답 수신 메모리 제한과 다릅니다.

제품 응용비동기 순서와 요청 History: 늦은 응답이 최신 화면을 덮지 않게 한다

Race condition은 완료 순서가 시작 순서와 달라 결과가 잘못 반영되는 문제입니다. 느린 A 다음 빠른 B를 보내면 B가 먼저 끝날 수 있습니다. A가 나중에 B 화면을 덮으면 사용자는 방금 보낸 요청과 다른 결과를 봅니다.

App은 새 job·Cancel·unmount에서 이전 effect cleanup을 합니다. active=false와 abort로 수명을 끝내고, 결과 callback은 active를 확인합니다. state updater에서도 현재 job.id와 완료한 job.id가 같은지 확인합니다. 취소를 무시하는 transport를 가정해도 오래된 결과를 반영하지 않도록 두 조건을 씁니다.

요청 이력은 최소 metadata만: method·정제 URL·시간·status·elapsed 등을 세션 메모리 최대 20개로 보관합니다. Params·Headers·Body·원응답·인증값을 그대로 저장하지 않습니다. query/hash/userinfo와 민감 경로를 제거하고, Reuse는 method와 정제 URL만 복원하며 자동 Send하지 않습니다. 모든 비밀 문자열을 완벽히 탐지하는 보장은 없습니다.

두 History 구분: DOM Lab의 History는 Tree snapshot으로 화면을 Undo/Redo합니다. API Studio의 History는 과거 요청의 안전한 요약을 다시 입력하는 기능입니다. 메모리 이력이므로 데이터베이스나 localStorage 영구 저장도 아닙니다.

실행 환경 이해TypeScript와 Node.js: 작성 언어·브라우저·개발 도구의 역할은 다르다

TypeScript는 JavaScript에 정적 타입 검사를 더한 작성 언어입니다. 현재 src는 strict TS이고 VNode·Operation·HookSlot·RequestResult처럼 가능한 형태를 union으로 구분합니다. 예를 들어 kind가 text이면 text 필드를, element이면 tag/children을 다루게 하여 잘못된 분기와 전달을 줄입니다.

tsc는 타입을 검사하고 브라우저가 실행할 ES module JavaScript를 dist에 생성합니다. 브라우저가 TypeScript 타입을 실행하는 것은 아닙니다. 타입이 지워진 뒤 들어오는 외부 JSON·DOM·사용자 입력은 실제 값 검증이 여전히 필요합니다.

Node.js는 브라우저 밖에서 JavaScript를 실행하는 환경입니다. 이 프로젝트에서는 빌드 스크립트·정적 개발 서버·테스트·테스트용 HTTP fixture를 실행합니다. 제품의 HTTP 요청은 브라우저 Fetch가 보내며, 별도 제품 API backend나 DBMS를 만든 것은 아닙니다.

Vanilla 제약: TypeScript를 썼어도 React·Vue 같은 외부 UI 엔진을 쓰지 않았습니다. HTML은 시작 host와 문서 구조, CSS는 표현, 자체 TS 엔진은 VDOM/상태/갱신을 맡습니다. Vitest/Playwright 등은 개발·테스트 도구입니다. dev는 처음 build한 뒤 정적 파일을 제공하고 source watch는 없으므로 수정 뒤 다시 build하고 reload해야 합니다.

과제 원문의 JavaScript 또는 TypeScript 허용 범위와 이후 사용자 승인에 따라 전환된 현재 코드를 설명했습니다. 과거 하네스의 JS 통일 문구를 현재 제품 언어로 오해하지 마세요.
